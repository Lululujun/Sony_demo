# 索尼动态分货 Agent Demo · 用户操作与字段说明书

## 1. 这套 Demo 演示什么

本 Demo 用确定性模拟数据演示“供给进入分货池后，如何在渠道需求、资金额度、履约质量、动销效率和库存状态之间做可解释分配”。页面会根据输入实时运行算法，不是 PPT 内容的网页化复述。

当前数据均为演示数据，不代表索尼真实经营数据；“回写 SAP”只在浏览器内生成锁单任务，不会访问外部系统。

## 2. 场景与 SKU 的关系

| 选择器 | 含义 | 切换后发生的变化 |
|---|---|---|
| 场景 | 一组业务环境假设，例如旺季缺货或淡季保供 | 变更缺货强度、淡旺季系数、可用 SKU 集合及默认 SKU |
| SKU | 当前场景中的一个完整产品数据快照 | 同时替换供给量、渠道数、需求、额度、权重、动销、库存、锁单卡和求解结果 |

场景与 SKU 不是一一对应。相同 SKU 可以出现在多个场景中，并因业务环境不同而拥有不同数据。例如 PS5 Pro 在“PPT 示意”“旺季缺货”“淡季保供”中分别有 168、150、200 台供给，并使用不同的需求和缺货参数。

切换场景时，如果当前 SKU 也存在于新场景，系统会保留该 SKU；否则自动选择新场景的默认 SKU。SKU 下拉框只显示当前场景允许的产品。

## 3. 推荐演示顺序

1. 选择“PPT 示意场景 / WH-1000XM6”，说明 210 台如何分成 A/B/C = 108/50/52。
2. 切换到 Alpha 7 V，指出渠道数从 3 变为 4、供给从 210 变为 105，分配轨道已完全重算。
3. 回到 WH-1000XM6，将中原电子-B 的“额度”从 50 调高，观察“额度触顶”标签和回流结构变化。
4. 点击“重算并回放”，逐步讲解公平层、封顶回流、效率层和整数尾差。
5. 进入“方案对比”，比较偏公平、均衡、偏效率三套参数方案。
6. 点击“回写 SAP”，演示部分锁单、支付确认、主动放弃和超时回流。
7. 进入“周转与校准”，展示库存估算置信带，并模拟周一库存真值到达。

## 4. 分货工作台输入字段

| 字段 | 单位/范围 | 含义 | 对算法的影响 |
|---|---|---|---|
| 今日可分货量 | 台，非负整数 | 当前 SKU 本轮可进入分货池的实物数量 | 决定公平池与效率池可使用的总量 |
| 需求 | 台，非负整数 | 渠道申报或预测的基础需求 | 是公平层的基础上限，也是需求满足率的分母 |
| 额度 | 台，非负整数 | 财务可用额度按当前 SKU 单价折算后的最大可承接数量 | 硬约束；任何层的最终分配都不能超过该值 |
| 权重 | 无量纲，通常约 0.5–1.8 | 渠道履约质量在公平层的相对权重 | 公平层有效权重 = 需求 × 履约权重 |
| 动销 | 无量纲指数，通常约 0.4–1.8 | 当前 SKU 在该渠道的相对销售速度/消化能力 | 参与效率层权重；值越高，越可能获得效率加配 |
| 公平预算 β | 0–1；页面常用 0.3–1.0 | 基础供给中倾向公平兜底的比例 | β 越高越平均覆盖，越低越强调效率倾斜 |
| 淡旺季系数 | 页面 0.7–1.4 | 大于 1 表示旺季，小于 1 表示淡季 | 旺季提高效率权重，并最多把 10 个百分点从公平池移向效率池 |
| 市场缺货度 | 0–1 | 0 为供应宽松，1 为极度稀缺 | 越缺货，越提高公平池占比，避免货量过度集中 |

### 4.1 “额度”为什么用台而不是元

页面里的额度是已经折算成数量的硬上限：

```text
额度折算数量 = floor（实时可用资金 / 当前 SKU 含税单价）
```

例如可用资金可覆盖 50 台，则页面显示额度 50。正式接入时可以同时展示金额，但算法最终使用整数台数，确保分配不会形成小数件。

分货阶段使用计算快照额度；锁单阶段会再次读取实时余额。因此渠道可能在分货时获得 50 台，但锁单时余额只覆盖 32 台，此时 32 台进入软锁，18 台立即回流。

### 4.2 “权重”是什么，不是什么

权重是相对优先系数，不是百分比，也不是最终可得台数。权重 1.5 表示在其他条件相同时，该渠道公平水位上升速度约为权重 1.0 渠道的 1.5 倍。渠道仍受需求和额度上限约束。

权重可以由历史履约、支付及时率、预测准确率等特征形成。本 Demo 用一个可编辑的综合履约权重代表这些特征。

### 4.3 “动销”与“估算去货量”的区别

- 工作台的“动销”是标准化相对指数；1.3 代表相对基准更快，不等于每天卖 1.3 台。
- 周转页的“估算去货量/估算日动销”是实物台数，由库存流量法估算。
- 周一校准会把库存偏差反馈到动销参数，但两者的单位仍不同。

## 5. 公平池比例

算法先根据缺货度把 β 向 1 推进：

```text
缺货调整后公平比例 = β + 缺货度 ×（1 − β）
```

再根据淡旺季调整，调整幅度最多 ±0.1：

```text
最终公平比例 = clamp（缺货调整后比例 + clamp（(1 − 淡旺季系数) × 0.1, −0.1, 0.1）, 0, 1）
公平池 = round（可分货量 × 最终公平比例）
效率池 = 可分货量 − 公平层实际分配量
```

缺货度高时，即使 β 较低，系统也会保留较大的公平兜底池；旺季系数高时，会适度增加效率倾斜。

## 6. 分配算法与页面图形

### 6.1 公平层（蓝色）

所有符合条件的渠道按同一满足率水位同步上升：

```text
公平分配_i(λ) = min（需求_i, 额度_i, λ × 需求_i × 履约权重_i）
```

渠道先触达需求线或额度线，就退出当前公平水位计算；它没用完的份额继续流给其他渠道。

### 6.2 效率层（绿色）

```text
效率权重_i = 动销_i × 淡旺季系数 × 库存健康倍率_i
库存健康倍率 = 断货风险 1.20 / 健康 1.00 / 积压 0.65
```

效率层允许最终分配超过基础需求，因此轨道可能穿过“需求”标记；但最终分配永远不能超过“额度”标记。库存置信度为“不可信”的渠道不参与效率层。

### 6.3 整数与守恒

精确比例通常不是整数。系统先向下取整，再把剩余单台按“小数余数从大到小”分配；余数相同则按渠道 ID 升序。这样同一输入永远得到同一输出，并满足：

```text
Σ 最终分配 ≤ 可分货量
最终分配_i ≤ 额度_i
所有分配量均为整数
```

若所有渠道都触达可承接上限，可能出现“未分完”；否则页面显示“守恒校验通过”。

### 6.4 横向分配轨道

| 图形元素 | 含义 |
|---|---|
| 蓝色段 | 公平层分配量 |
| 绿色段 | 效率层追加量 |
| 灰色竖线“需求” | 渠道基础需求位置 |
| 橙色竖线“额度” | 财务可承接硬上限 |
| 右侧台数 | 当前回放帧或最终分配 |
| 右侧百分比 | 单渠道满足率 = 最终分配 / 需求；允许超过 100% |

### 6.5 顶部指标

| 指标 | 计算方法 |
|---|---|
| 可分货量 | 当前 SKU 本轮供给池 |
| 覆盖经销商 | 最终分配大于 0 的渠道数 / 当前 SKU 渠道总数 |
| 需求满足率 | Σ min（最终分配, 需求）/ Σ 需求 |
| 释放回流 | 锁单阶段因额度不足、主动放弃或超时而重新回到可分池的数量 |

整体需求满足率会把超过需求的效率加配截断到需求计算，因此不会超过 100%；单渠道轨道满足率可以超过 100%，用于说明该渠道获得了效率加配。

## 7. “分配明细”逐列解释

| 列名 | 含义 |
|---|---|
| 经销商 | 渠道名称与演示 ID |
| 需求 | 当前 SKU 的渠道基础需求 |
| 额度 | 资金余额折算后的最大承接台数 |
| 公平层 | 按统一公平水位分得的数量，不超过 min（需求, 额度） |
| 效率层 | 公平层之后按动销和库存健康追加的数量 |
| 最终分配 | 公平层 + 效率层 |
| 满足率 | 最终分配 / 需求 |
| 展开箭头 | 打开该渠道的完整求解审计轨迹 |

展开后的轨迹事件：

- `校验`：检查需求、额度、权重和库存可信度；
- `创建池`：生成公平池或效率池；
- `进入求解`：渠道满足该层参与条件；
- `注入`：按当前水位分配一批台数；
- `尾数`：整数尾差按最大余数规则分配；
- `需求封顶`：公平层达到需求，但仍可能参加效率层；
- `额度封顶`：达到硬上限，不再接受分配；
- `仅保底`：库存不可信或不满足效率层条件；
- `池量用尽`：该层结束；
- `未分完`：所有渠道都封顶后仍有剩余；
- `完成`：输出最终结果与守恒校验。

## 8. 标签说明

### 8.1 分配结果标签

| 标签 | 触发条件 | 业务含义 |
|---|---|---|
| 分配完成 | 已分配但未超过需求，且没有被额度卡住 | 正常完成本轮分货 |
| 效率加配 | 最终分配大于需求 | 渠道动销和库存状态支持额外倾斜 |
| 额度触顶 | 最终分配达到额度上限 | 资金是当前主要约束，多余份额已回流 |
| 仅保底 | 库存置信度为不可信 | 只参加公平层，避免错误库存导致效率倾斜 |
| 守恒 / 守恒校验通过 | 总量、额度、整数检查均通过 | 算法输出满足硬约束 |

### 8.2 库存健康标签

| 标签 | 含义 | 效率层倍率 |
|---|---|---:|
| 断货风险 | 库存相对历史分货偏低，需要防止断货 | 1.20 |
| 健康 | 库存处于正常区间 | 1.00 |
| 积压 | 库存相对历史分货偏高 | 0.65 |

健康标签不是对渠道价值的评价，只表示当前 SKU 的库存位置。

### 8.3 库存置信度

| 标签 | 含义 | 下一轮处理 |
|---|---|---|
| 高 / 中 / 低 | 库存估算仍可用于效率判断，但不确定性逐级增加 | 正常参与；置信带宽度不同 |
| 不可信 | 真值与估算偏差超过阈值，或数据质量异常 | 仅走公平保底 |

### 8.4 锁单状态标签

| 标签 | 状态 | 说明 |
|---|---|---|
| 待锁单 | `ALLOCATED` | 已有分货结果，尚未发起额度实时校验 |
| 待支付 | `SOFT_LOCKED` | 实时额度校验通过，货量暂时锁定 |
| 已支付 | `CONFIRMED` | 支付确认，货量正式锁定 |
| 主动放弃 | `WAIVED` | 渠道主动释放，不扣履约分 |
| 支付超时 | `RELEASED / PAYMENT_TIMEOUT` | 软锁过期，释放货量并扣履约分 |
| 额度释放 | `RELEASED / CREDIT_*` | 实时额度无法覆盖，未锁部分立即回流 |

## 9. 方案对比页

三套方案使用同一 SKU 的供给、需求和额度，只改变 β：

| 方案 | β | 倾向 |
|---|---:|---|
| 方案 A · 偏公平 | 0.9 | 提高渠道覆盖和基础满足 |
| 方案 C · 均衡 | 0.7 | 兼顾覆盖与动销，Demo 默认推荐 |
| 方案 B · 偏效率 | 0.5 | 更多货量进入效率层，可能提高集中度 |

指标含义：

- 覆盖经销商：最终获得至少 1 台的渠道数；
- 预计缺货率：`1 − 整体需求满足率`；
- 整体周转指数：按最终分配量加权后的动销指数，再除以当前最高动销；
- 分货集中度：各渠道分配占比平方和。越高表示货量越集中；
- 差异最大：同一渠道在三套方案中的最大值减最小值；
- 守恒：三套方案分别满足各自总量约束。

点击“采用此方案”会把对应 β 和求解结果带回工作台。

## 10. 锁单看板

```text
待锁单 → 实时额度校验 → 软锁定 → 支付确认
                          ↘ 主动放弃
                          ↘ 支付超时 → 释放回流
```

关键规则：

- 实时额度全部覆盖：全部数量进入软锁；
- 实时额度部分覆盖：可覆盖部分进入软锁，差额立即回流；
- 实时额度为 0：整单释放，不记超时违约；
- 主动放弃：释放当前可释放量，不扣履约分；
- 支付确认：履约分 `+2`；
- 支付超时：释放软锁量，履约分 `−5`；
- “释放回流”会同步回工作台顶部指标。

锁单卡中的“金额”按 `锁定或分配台数 × SKU 演示单价` 计算，只用于说明额度与高客单价 SKU 的关系。

## 11. 周转与校准页

### 11.1 库存流量字段

| 字段 | 含义 |
|---|---|
| 期初 | 本周期开始时的渠道库存 |
| 入库 | 本期分货后进入渠道的数量 |
| 期末 | 当前估算或上传的期末库存 |
| 估算去货 | `期初库存 + 本期分货入库 − 期末库存` |
| 去货率 | 估算去货量 / 可销售库存 |
| 经销商侧周转 | 当前库存 / 渠道平均周分货量，主决策口径 |
| 总部/仓库周转 | 总部库存系统口径，作为参考 |

### 11.2 14 天库存估算与置信带

```text
日库存估算 = 最近周一库存真值 + 累计分货入库 − 累计估算去货
```

- 深色点：周一到达的库存真值；
- 蓝色虚线：每日库存估算；
- 浅蓝带：估算置信区间；
- 上界用于补货判断，下界用于保供判断；
- 距离周一越远，误差累积越多，置信带越宽；下一个周一真值到达后重新收窄。

### 11.3 周初校准

- 绝对偏差不超过 12 台：保留可信状态，并对动销做小步微调；
- 绝对偏差超过 12 台：标记“不可信”，下一轮只走公平保底；
- 应用校准后，动销、库存、置信度和库存健康标签同步到工作台。

## 12. 权重设置抽屉

| 因子 | 当前 Demo 行为 |
|---|---|
| 淡旺季 | 直接修改场景淡旺季系数 |
| 缺货度 | 直接修改市场缺货度 |
| 动销效率 | 按比例缩放当前所有渠道的动销指数，保留渠道相对差异 |
| 履约质量 | 按比例缩放当前所有渠道的履约权重，保留渠道相对差异 |
| 库存健康 | 对断货风险渠道提高效率倾向，对积压渠道降低效率倾向 |

“自动更新/人工覆盖”是演示配置状态：拖动后显示人工覆盖；“恢复自动基线”会恢复当前“场景 + SKU”的预置参数，而不是恢复场景的其他默认 SKU。

“近 8 周更新效果”为固定演示曲线，用来说明正式系统可展示权重版本与准确率趋势，不会反向影响本轮求解。

## 13. 按钮与运行行为

| 操作 | 结果 |
|---|---|
| 重算并回放 | 从第一条可视化分配事件开始播放，不改变输入 |
| 分步 | 每次推进一个求解事件 |
| 1× / 2× | 改变回放速度 |
| 导出 | 下载当前场景与 SKU 的 UTF-8 CSV 分配结果 |
| 回写 SAP | 模拟生成锁单订单并跳转锁单看板 |
| 运行一天 | 日期 +1，并依次模拟库存重估、重新分货、锁单推进和看板刷新 |
| 至下周一 | 跳到下一个周一并打开库存校准弹窗 |
| 重置 | 恢复 PPT 示意场景 / WH-1000XM6 的固定基线 |

| 渠道需求 | 订单、渠道预测、销售计划 |
| 额度金额与折算量 | 财务额度服务、实时余额、价格服务 |
| 履约权重 | 支付及时率、锁单成功率、主动放弃率、预测准确率 |
| 动销指数 | POS、渠道库存流量、销量预测 |
| 库存真值 | 周期盘点、渠道上传、API 对账 |
| 锁单状态 | 订单服务、支付服务、超时任务 |
| 审计轨迹 | 分货决策服务的输入版本、参数版本、事件日志 |

正式上线时应把“场景 + SKU + 数据快照时间 + 参数版本”作为一次求解的联合标识，避免跨产品、跨时点混用数据。

## 15. 常见问题

### 为什么最终分配会高于需求？

需求是公平层的基础需求线，不是全流程硬上限。效率层允许给高动销且库存可信的渠道加配，但不会超过额度。

### 为什么额度比需求小的渠道很快封顶？

公平层上限是 `min（需求, 额度）`。资金只能覆盖较少台数时，额度成为硬上限，剩余货量回流给其他渠道。

### 为什么提高缺货度反而增加公平池？

极度缺货时，如果仍大量按效率集中，部分渠道可能完全断供。缺货度用于提高基本覆盖保护；旺季系数再在此基础上适度恢复效率倾斜。

### 为什么“仅保底”渠道仍能获得货？

“仅保底”不是禁配，而是禁用效率加配。它仍可在公平层获得基础分配，以避免数据质量问题直接导致断供。

### 为什么切换 SKU 会重置刚才的编辑？

每个 SKU 是独立基线快照。保留上一 SKU 的编辑会把某产品的需求或额度错误带入另一产品，因此切换时恢复目标 SKU 的完整数据集。
